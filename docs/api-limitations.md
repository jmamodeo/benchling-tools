# API limitations

These limits are based on the public Benchling documentation and OpenAPI contracts. The document, unstructured-table, and entry-field portions were rechecked against the V3 spec captured on 2026-11-19.

- Read-only bulk entry lookup uses V2 `GET /entries:bulk-get`, specifying exactly one of `entryIds` or `displayIds`. Benchling documents a maximum of 100 IDs per call, so the CLI and MCP split larger requests into 100-ID chunks. See [Bulk Get Entries](https://docs.benchling.com/docs/api/v2/benchling-api/entries/bulk-get-entries). Template structure uses V2 `GET /entry-templates/{entry_template_id}` because V3 `EntryTemplate.Get` returns metadata only; the summary reports ordered note types, result-table schema IDs, table names, section titles, and short text previews. `template list` reads one V2 page with optional name filtering. Folder retrieval uses V3 `GET /folder/{folder_id}`.
- Entry creation uses documented V3 `Entry.Create` (`POST /api/v3/entry`), whose `CreateEntryInput` includes `entryTemplateId`, `folderId`, `name`, and `schemaFields`. The V3 API contract also has `GET /entry-template/{entry_template_id}` and `GET /folder/{folder_id}`; plans read these resources and reject missing or archived resources before any write. The create response is expected to be an `Entry` with an `id`, as specified by the contract. This path has not been live-verified. Preview does not lock or reserve the template/folder: they may change or become inaccessible after planning, in which case Benchling can reject apply. Creation is never retried, and the plan is spent on any attempt. After creation, use the returned ID with `entry inspect` or `results tables`; the entry's results-table IDs are read from the created entry.
- `web_url` is the entry's link in the Benchling web app. V3 [Get Entry by ID](https://docs.benchling.com/docs/api/benchling-api/entry/get) defines `webUrl` as "Specifies the absolute URL of the entry in the Benchling web app." V2 entries carry `webURL` ("URL of the entry"). The toolkit passes the value through as returned and does not build or rewrite it; a missing or empty value is `null`, and a `next_step` then names the entry by ID only. Entry create returns the `webUrl` of the create response's `Entry`. A results upload records the V2 `webURL` from the `GET /entries/{entry_id}` read it already makes to find the result table, at preview and again at apply. Assumptions the docs do not state, not verified against a live tenant: the V3 `webUrl` and V2 `webURL` open the same page, the link does not change while the entry exists, and the create response includes `webUrl`.
- The V3 Document API is beta. This client sends `EARLY-ACCESS: true` and uses the unified `/api/v3` routes.
- Entry content is an ordered, flat list. Sections are derived from section markers; they are not independent nested resources.
- Unstructured-table reads return `rows` as a URL. This client pages `.../rows/items` at `pageSize` 100, the maximum the API accepts. `set_cells` sends `update_table_cells` and `append_rows` sends `insert_table_rows` on `PATCH /entry/{id}`. There is no full-table replace.
- Those cell and row writes reset table evaluation (`isEvaluated` becomes false). Benchling's browser recalculates formulas.
- `DocumentPartResultsTable` parts are readable, including typed columns and paged rows. Their cells are not editable here. Registration, inventory, and other structured tables are still not readable or editable through the document API. `DocumentPartUnavailable` parts are reported as unavailable rather than kept as an unknown type.
- `benchling-tools results rows` and the MCP tool `results_rows` read one page from `GET /document-part-results-table/{id}/rows/items`. `pageSize` is 1 to 100 and defaults to 50. `nextToken` resumes the following page. The part is loaded first, and its `rows` URL must be that path on the same tenant. `entry get --full` still reads every row of the part. The `{id}` is a document-part id (`docpart_…`); the V3 contract marks the `strtbl_…` handle as deprecated in favour of `documentPartResultsTableId` (`docpart_XXXXXXXX`). A `strtbl_…` id is mapped to a part only with an entry, by handle (`apiId` or `tableHandleId`), then result schema, then name within that schema, then the only results-table part; otherwise it is refused as a `validation_error` rather than sent to the rows endpoint.
- Benchling has no server-side filter on text field values of results, so `results tables --where` and `results rows --where` (MCP `where`) filter table rows client-side. V3 [`GET /result/items`](https://docs.benchling.com/docs/api/benchling-api/result/list) filters by `entry.eq`/`anyOf`, `schema.eq`/`anyOf`, `creator.anyOf`, `project.eq`, created and modified time, `id.anyOf`, and link values only (`schemaFieldLinkValue.linkedItemIds`, `schemaFieldLinkValue.schemaFieldIds`). V2 [`GET /assay-results`](https://docs.benchling.com/docs/api/v2/benchling-api/assay-results/list-assay-results) filters by `schemaId`, created and modified time, `entityIds` and `storageIds` (20 each at most), `assayRunIds`, `automationOutputProcessorId` and `ids`. The rows come from [`GET /document-part-results-table/{id}/rows/items`](https://docs.benchling.com/docs/api/benchling-api/document-part-results-table/rows-list), paged at `pageSize` 100 at most ([Working with tables](https://docs.benchling.com/docs/working-with-tables)), so `results tables --where` reads every row of each selected table. Row counts come from `rowCount` and `submissionStatus` on each `DocumentPartResultsTable` in one [parts listing](https://docs.benchling.com/docs/api/benchling-api/entry/parts-list). Pending results are not table rows until a person accepts them ([Creating a new notebook entry containing results](https://docs.benchling.com/docs/creating-a-new-notebook-entry-containing-results)), so `--where` counts accepted rows only; `results pending` reads pending ones.
- `results diff` (MCP `results_diff`) reads every row of each results table with V3 [List rows](https://docs.benchling.com/docs/api/benchling-api/document-part-results-table/rows-list). Benchling has no server-side filter on a text value: neither the rows list nor V2 [List assay results](https://docs.benchling.com/docs/api/v2/benchling-api/assay-results/list-assay-results) nor V3 [List results](https://docs.benchling.com/docs/api/benchling-api/result/list) filters by a field's text, so a `:RUN_VALUE` selects rows locally after the whole table is read. Pending results are not table rows and are not compared. Link cells hold ids, not barcodes; `--resolve-barcodes` reads them with V2 [Bulk get containers](https://docs.benchling.com/docs/api/v2/benchling-api/containers/bulk-get-containers) (`containerIds`, "Comma-separated list of container IDs"), at most 100 ids per call. That limit is the toolkit's; the contract states none. Assumptions not verified against a live tenant: bulk-get omits a container it cannot return rather than failing (an error is surfaced as is, and an omitted id is listed under `containers.unresolved`); a container link's value is an `ObjectLinkValue` whose `__typename` is `Container`, or a bare `con_…` id; and an attachment cell's value is an `Attachment` link or a blob id in a column whose field definition is an attachment field.
- Re-syncing a results table is UI-only. After `PATCH /result/{id}`, a notebook results-table cell can keep the old value until a person uses **Re-sync table** in the Benchling web app. The recorded V3 contract has only GET routes for results tables: `DocumentPartResultsTable.Get` on `/document-part-results-table/{id}` and `DocumentPartResultsTable.rows.List` on its `rows/items`. The `PATCH /entry/{id}` `partsMutation` operation types are `insert`, `delete`, `move`, `update_table_cells` and `insert_table_rows`. None of them re-syncs a table. The V2 contract has no table re-sync route either. The toolkit therefore has no re-sync command. `results rows` and `results get` detect the stale cell by comparing each submitted row's cells with its linked record (`SchemaFieldColumnDefinition.fieldDefinitionApiId`, "the API identifier of the schema field definition for this column", against `schemaFields[].fieldDefinition.id`), and warn.
- `benchling-tools export` and the MCP tool `export` do not call a Benchling export endpoint. They page the existing reads: unstructured-table rows at `pageSize` 100, results-table rows at `pageSize` 100 until `nextToken` is absent, and assay results from `GET /result/items` at `pageSize` 100. The rows are written to a local JSON or CSV file. The response is a summary (row count, column names, path, SHA-256) and does not include the rows. A cell is the evaluation when Benchling returned one, otherwise the input. An existing file is not replaced unless overwrite is set. Nothing is written to Benchling. `--part` for `table` and `results-table` is a `v3_document_part` id (`docpart_…`) from `entry inspect`. `results tables` returns `v2_structured_table` ids (`strtbl_…`). `export --kind results-table --part strtbl_… --entry ENTRY` resolves that id through the entry's document parts, or reads assay results for the entry and the table's result schema when no results-table part matches. A `strtbl_…` id without `--entry`, or with `--kind table`, is a validation error that names `v3_document_part`. V3 result measurements are `schemaFields` (field-definition id plus `BenchlingValue`), not a V2 `fields` map. Assay-result export adds one column per field, named with the field definition's display name. Link values, including results-table and unstructured-table cells, are the linked ids. An unset result field is empty (`""` in CSV, `null` in JSON). `linkedEntityId` is omitted when it is the result's own id or the field is not a link.
- Document insert uses `position`, delete uses `sourceRange`, and move uses `sourceRange` plus `destinationPosition`. A part ID means immediately before that part. A move that would leave the entry starting with anything other than a section fails in preview with `Entry must start with a section`, before a plan is saved. These mutations and unstructured table updates send the entry version from `versionMetadata.versionId` and return HTTP 409 when it is stale. Entry schema-field updates do not publish an equivalent atomic version precondition. This client compares affected values immediately before writing and labels that protection as best effort.
- Entry field inputs may use a V3 field `systemName` or its field-definition ID. Plans show both and send the field-definition ID (`tsf_…`), which is what `schemaFields` accepts. V2 result uploads still use the result field's `systemName`. Display names are rejected there because they are mutable and may not be unique. A V3 result update resolves a mapped CSV column to a field-definition id and sends that id.
- `changes plan --family results --csv` reads a CSV file. `--id-column` names the result id (export writes `id`). Each `--map CSV_COLUMN=FIELD` is required; columns are not inferred. `FIELD` may be the export display name, the system name, or the field-definition id. Unknown columns, ambiguous names, and bad rows are one validation error and nothing is written. Unmapped columns are left unchanged. A blank cell clears a value that is present. A blank cell on an empty field is not a change: export writes both null and an empty string as a blank cell, so an unmodified export does not clear those fields. The plan stores each result's `modifiedAt` and the mapped values. Apply re-reads every result and sends `PATCH /result/{result_id}` only when those still match. `UpdateResultInput` has no version property, so `modifiedAt` is the version precondition. The body is `schemaFields` keyed by field-definition id. The limit is 500 rows. A later PATCH failure leaves earlier PATCH results in the journal as partial completion.
- Replacing a text part requires insert followed by delete. If the second request fails, the entry contains both parts and the journal reports partial completion.
- Results created through the API land as pending. Benchling's V3 guide says: "When results are created in this way, they are not immediately appended to the destination table. Their source is marked as "pending" and they will not appear in the table until they are explicitly integrated." A person integrates them with the plug icon in the table toolbar. The same holds for V2 `assay-results:bulk-create` with a `tableId`, so this is not specific to one API version. The public V2 and V3 specs have no call that accepts pending results. The accept control may insert every pending result that matches the table's schema, so avoid stray or test results. Results created without a table id are not attached to a table at all. After an upload, `changes apply` returns `next_step` naming all submitted tables; partial or unconfirmed submissions also include it when acceptance may be needed.
- Live verification on 2026-09-29 against a Benchling tenant found that it rejects `assayResults[].id` in notebook-table bulk uploads, even though public V2 `AssayResultCreate` declares it. The CLI omits remote IDs, retains local correlation UUIDs plus task IDs, and never treats those local UUIDs as idempotency keys. Fresh plans are required for the updated contract; plans using the old request shape cannot be applied. This toolkit caps each table upload at 500 records.
- A results upload plan can contain multiple table batches. Each batch is independently checked against its table and schema and submitted with its own bulk-create request. The 500-record cap per table batch is this toolkit's own batch size, not a Benchling limit: V2 [`POST /assay-results:bulk-create`](https://docs.benchling.com/docs/api/v2/benchling-api/assay-results/bulk-create-assay-results) says "Bulk create results. Limit of 4000 results per request." (see also [rate limiting](https://docs.benchling.com/docs/rate-limiting)). Split more rows into several plans. A definite failure on one batch does not stop attempts for other batches; an ambiguous write remains unknown and is never retried automatically.
- A notebook results table holds at most 1,000 rows. Benchling Help, [Capture data with Results](https://help.benchling.com/hc/en-us/articles/39954660101773-Capture-data-with-Results): "Result tables cannot have more than 1000 rows." [Standardize data capture with structured tables](https://help.benchling.com/hc/en-us/articles/39940813149709-Standardize-data-capture-with-structured-tables): "Tables are limited to 1,000 rows and 255 columns." The limit was raised from 500 rows in 2025 ([announcement](https://community.benchling.com/announcements-48/1000-row-structured-tables-are-now-in-limited-availability-1582)). A bulk-create task over the limit fails with "Specified table does not have capacity for the provided results", possibly after sibling tables in the same run were written. `changes plan --family results` and `results capacity` therefore read each table's V3 `rowCount` from [`GET /document-part-results-table/{id}`](https://docs.benchling.com/docs/api/benchling-api/document-part-results-table/get), with parts listed by [`GET /entry/{id}/parts/items`](https://docs.benchling.com/docs/api/benchling-api/entry/parts-list) (see [Working with tables](https://docs.benchling.com/docs/working-with-tables)), and refuse a plan that would pass 1,000 rows before staging anything. A blank `UNSUBMITTED` placeholder row counts as 0 used. A `strtbl_…` table with no single matching V3 part is reported as `unknown` and not checked.
- Created results "are marked as pending until someone integrates them with the plug icon in the table's toolbar" ([Creating a new notebook entry containing results](https://docs.benchling.com/docs/creating-a-new-notebook-entry-containing-results)). The docs do not say whether pending results count toward the 1,000-row limit, so the toolkit reports both `remaining_without_pending` and `remaining_with_pending` and does not guess: a plan that fits only without pending results is saved with an `unknown_pending` warning. Only pending results from this home's applied plans are known; `results capacity --include-schema-pending --created-after T` also counts the schema's pending results on any entry, for information.
- The V2 OpenAPI snapshot's task error example uses an `errors` object with an `index`, while its task schema allows errors as either an object or an array of objects and does not specify their complete shape. The implementation assumes the example's `index: 0` identifies the first input row; the contract does not explicitly state the index base. Status maps only a non-boolean, in-range integer `index` to the batch's zero-based input row and local correlation ID. It preserves the raw error in the mapping and reports entries without a usable index under `unmatched_row_errors`; it does not infer a row from list order or other fields. This is intentionally conservative and should be revisited if Benchling documents more.
- `changes status --wait --timeout SECONDS` and MCP `changes_status` poll every submitted task with bounded exponential backoff; the default status call reads each task once. On timeout, still-running tasks remain marked `submission_running`. Confirmed task result IDs and task statuses are persisted locally for reconciliation.
- Current V3 document-part responses are flattened `DocumentPart*` objects. Reads preserve these objects and support both flattened and legacy nested content. Unknown types are explicitly retained as opaque data. V2 get responses wrap their object (for example `entry`, `project`, `folder`); adapters unwrap and validate these instead of silently reporting empty data. Tasks can be flat status objects without IDs.
- Pending result uploads have no entry (`entryId`/`entry` is null) until a person accepts them in the table. A CSV update of such a result is refused with "Result is not on the selected entry", and the message says to accept the pending results first. After a result is accepted, `PATCH /result/{id}` changes the result record. A live check on a development tenant found that the notebook results-table cell still showed the old value afterward, so re-read the result, not the table cell, to confirm an update. An Entry Link schema-field value is a distinct relationship and does not make the pending result appear in the V3 `entry.eq` filter. Read pending records by the canonical V3 IDs returned in the task instead.
- V2 `AssayResult` has `id` (a UUID) and `v3Id` ("V3 identifier for the result"); the V3 `Result` has only its `result_…` `id`, and V2 has no lookup by V3 id. `results get`, `results list`, `results pending` and `results verify` accept either id. A V2 UUID is mapped to V3 through bulk-get's `v3Id`. A V3 id is mapped to V2 by reading V2 `GET /assay-results` for the record's schema from a second before to a second after its `createdAt` (`createdAt.gte`, `createdAt.lte`, `archiveReason=ANY_ARCHIVED_OR_NOT_ARCHIVED`, `sort=createdAt:asc`) and matching `v3Id`. Records created within two seconds of each other share one window, read for at most 5 pages plus one per hundred ids; when that finds nothing, `v2_id` is null (or, for `results pending`, the id is `not_found`). A V3 id is never sent to `assayResultIds`, which a tenant answered with HTTP 400 "One or more provided assayResultIds were invalid".
- `results pending` and `results verify` (MCP `results_pending` and `results_verify`) read pushed results with V2 `GET /assay-results:bulk-get` (`assayResultIds`, documented as "Up to 200 IDs can be specified at once"; the toolkit sends at most 200 per request) and V2 `GET /assay-results` (`schemaId`, `createdAt.gte`, `pageSize` up to 100, `nextToken`). V2 list has no entry filter, so the schema and time window can include results pushed to other entries. V3 `GET /result/items` filters by `entry.eq`, but a pending result has no entry until it is accepted, and neither API filters by pending state, so `results pending --entry` reads the record IDs of the applied result upload plans for that entry stored in this home's plans and journals; plans applied from another home are not known. Assumptions the docs do not state: a result is `pending` when V2 `entryId` is null and `accepted` when it is set, and `archived` when `archiveRecord` is present; bulk-get omits IDs it cannot return rather than failing the request, and those IDs are reported as `not_found` (if Benchling instead returns an error, it is surfaced as is); a V2 field's `value` has the same shape as the planned `{"value": ...}` (numbers compare by value and lists of strings without order, but other values, such as datetimes, must match exactly). The task response does not document whether `assayResults` follows the input order, so verify pairs planned rows with fetched records by exact field match first and only then in order. Record IDs come from the plan journal; when `changes status` has not stored them, the task is read once and the journal is not written.
- A result plan verifies its `strtbl_…` identifier against the selected entry's V2 `results_table` note, enforces that note's result schema, validates required fields, and checks supplied project IDs. Those reads do not establish write permission; Benchling remains authoritative at submission time.
- Result attachment fields take a blob ID. The V3 contract says an attachment value is "the ID of an attachment that has already been uploaded (upload files first with POST /v2/blobs)", and its `Attachment` model notes that "In the V2 API the same model is named Blob". A `{"file": PATH}` value (or a CSV cell `file:PATH`) on such a field is uploaded with V2 [Create blob](https://docs.benchling.com/docs/api/v2/benchling-api/blobs/create-blob) (`POST /blobs`, base64 `data64` and the MD5 of the raw bytes) when the file is at most 10,000,000 bytes. Larger files use [Create multipart blob](https://docs.benchling.com/docs/api/v2/benchling-api/blobs/create-multipart-blob), [Create blob part](https://docs.benchling.com/docs/api/v2/benchling-api/blobs/create-blob-part) in 10 MiB parts, and [Complete multipart blob](https://docs.benchling.com/docs/api/v2/benchling-api/blobs/complete-multipart-blob). The contract recommends multipart above 10MB and requires every part but the last to be at least 5MB. A multipart step that fails after the start sends one `:abort-upload`; the abort's outcome is journaled and the original error is raised. No upload request is retried. The per-file cap is 100 MiB and the per-plan total 1 GiB; these are toolkit limits, not Benchling ones. `blob get` and MCP `blob_get` use [Get blob](https://docs.benchling.com/docs/api/v2/benchling-api/blobs/get-blob) for metadata only. Assumptions the docs do not settle, not verified against a live tenant: the V2 blob ID is accepted as the value of a result attachment field by both V2 `assay-results:bulk-create` and V3 `PATCH /result/{id}`; an attachment field is recognized by the `__typename` `AttachmentLinkFieldDefinition` (or `BlobLinkFieldDefinition`, or a `type` of `ATTACHMENT_LINK` or `blob_link`); `md5` is the lowercase hex digest, as in the `eTag` example; each part's `eTag` is sent back unchanged to complete the upload; the `uploadStatus` returned by create or complete is recorded and not polled, so a blob still `IN_PROGRESS` is linked as returned; and Benchling does not document whether an unlinked or aborted blob is ever cleaned up. `results verify` compares an uploaded attachment field by the blob ID the journal recorded, assuming V2 `assay-results:bulk-get` returns that blob ID as the field's `value`.
- A write that times out is never retried automatically. Its journal status is `unknown` until reconciled.
- Plans are guarded by per-plan cross-process locks, so a CLI and MCP process cannot intentionally apply the same plan concurrently. A plan with any prior attempt is not reusable.
- Full entry reads combine entry metadata, document parts, schemas, V2 entry fields, and result records from several calls. The client reads the entry version before and after assembly, but linked results do not share that atomic document version; their independent retrieval timing and page count are reported separately.
- Attachment metadata and temporary download URLs may be returned. Attachment binaries are not downloaded by `entry get --full`.
- `blob get` uses V2 `GET /blobs/{blob_id}` or V3 `GET /attachment/{attachment_id}`; `blob download` uses V2 `GET /blobs/{blob_id}/download-url` or the V3 attachment's `downloadUrl`. See the official [V2 API specification](https://benchling.com/api/v2/openapi.yaml) and [V3 API specification](https://benchling.com/api/v3/openapi.yaml) for these endpoints. Neither metadata schema documents a size, checksum, or mapping from an `attachment_…` ID to a blob UUID. Verification therefore compares downloaded bytes only to caller-supplied expectations or a local reference; it does not verify against Benchling metadata. Without expectations, `verified` is false. Temporary download URLs are not returned by `blob get` or `blob download`.
- Authentication is app client credentials, one saved environment at a time (`benchling-tools auth login --env NAME`, optionally `--tenant-url`, `--client-id`, and `--secret-stdin`). The tenant URL is normalized (bare host, trailing slash, or a trailing `/api/v2` or `/api/v3`); `http://` is rejected. The tenant URL and client ID are stored in `environments.json`; the client secret is stored in the OS keychain, with no plaintext fallback. On Linux that keychain is Secret Service on the session bus, and the MCP client must pass `DBUS_SESSION_BUS_ADDRESS` because the SDK's default environment does not. Every CLI command and MCP tool call names its environment explicitly. App permissions, not the browser user's permissions, control API access. The Benchling app must be granted access to specific projects. Personal keys, delegated login, and saved profiles are not supported.
- Protected environments are a client-side guard only. The `protected` flag lives in the local `environments.json` and controls `changes apply` (`--env` on the command line plus a matching `--confirm-env`) and the MCP refusal message. Benchling has no matching setting, and the app's project permissions in Benchling remain the real limit. Anyone who can edit the state directory, or who uses the same app credentials through another client, is not stopped by it. Reads and previews are not guarded.
- The `examples/results-*.json` fixtures follow the documented `AssayResultCreate` shape (`schemaId`, `fields` keyed by system name with `{"value": ...}`) and are checked against the vendored V2 OpenAPI request schema and the offline fake. They have not been sent to a live tenant. Their table and schema IDs exist only in the fake.
- Benchling's official Python SDK currently targets V2. This package uses HTTPX for both API versions.
- V3 `GET /entry/items` applies `project.eq`, `schema.eq`, `name.anyOf` (exact, case-insensitive, not a substring), and inclusive `modifiedAt.gte` / `modifiedAt.lte`. It has no folder parameter. Live tenants ignore `folderId` on that route, so this client does not send it. A folder filter sends the whole query to V2 `GET /entries`, where `folderId`, `projectId`, `schemaId`, `names.anyOf`, and `modifiedAt` are server-side together. A name that contains a comma cannot be one item of `name.anyOf` or `names.anyOf`: both are comma-separated and the contract documents no escape. That name is sent as V2 `name`, with the other filters on the same V2 query. V2 `name` is a single entry name. The contract describes it as the specified name and does not say the comparison is case-insensitive. Nothing in an entry list is filtered in the client. A bare date is the start or end of that UTC day. A timestamp must include a time zone; a value with no zone is rejected. V2 documents `>` and `<` comparisons; this client sends `>=` and `<=` so the bounds stay inclusive. Listing `modified_at` values are UTC timestamps with a `Z` suffix. V2 responses that use `+00:00` are rewritten, and other offsets are converted to UTC.
- Schema lists page through `/entry-schema/items`, `/entity-schema/items`, `/result-schema/items`, and `/run-schema/items`. The caller's page defaults to 50 and stops at 100 so a large tenant is not returned in one response. `schema find` sends the exact, case-sensitive name filter to each selected collection, follows all pages to distinguish no match from ambiguity, then reads the matching schema and its field definitions. `schema get` without an explicit kind selects the entity schema route for IDs beginning with `es_`; this is based on the entity-schema ID namespace. `schema find` uses the discovered kind explicitly instead. Dropdown options come from `/dropdown/{dropdown_id}` and the unpaginated `/dropdown/{dropdown_id}/options/items`. The deprecated dropdown-option list is not used. Result-plan previews validate dropdown IDs against these loaded options and resolve linked values with read-only `GET` calls to the custom-entity, DNA-sequence, or amino-acid-sequence resource selected by the ID prefix. Linked-object schema IDs, including not-found results, are cached for the duration of a preview. This resolution supports only those three ID namespaces; other linked object kinds are reported as unresolvable rather than accepted without validation.
- `container find` with several `--barcode` values uses V2 [List containers](https://docs.benchling.com/docs/api/v2/benchling-api/containers/list-containers). Its `barcodes` parameter is a "Comma-separated list of barcodes. Matches all of the provided barcodes, or returns a 400 error that includes a list of which barcodes are invalid." `pageSize` defaults to 50 with a maximum of 100, so the toolkit sends at most 100 barcodes per request at `pageSize` 100 and follows `nextToken`. On a 400 whose body has `error.invalidBarcodes`, those barcodes are reported in `invalid_barcodes` and the rest of that chunk is requested once more; any other 400 is raised. A single value may not contain a comma. `entity_registry_id` is the container content entity's `entityRegistryId` when the response carries it; a batch's entity is a summary without one, and no per-entity lookup is made. `archiveReason` is not sent, so Benchling's default (`NOT_ARCHIVED`) applies and an archived container's barcode is reported in `missing_barcodes`. [Bulk get containers](https://docs.benchling.com/docs/api/v2/benchling-api/containers/bulk-get-containers) also takes `barcodes` but is not used.
- `container find --contents`, `--registry-id` and `--in` use V2 [List containers](https://docs.benchling.com/docs/api/v2/benchling-api/containers/list-containers) `storageContentsIds` ("Comma-separated list of IDs of entities. Restricts results to those that hold containers with at least one of the specified entities.") and `ancestorStorageId` ("ID of a plate, box, or location. Restricts results to those located in the specified inventory."). The docs give no maximum for `storageContentsIds`, so the toolkit sends 100 entity IDs per request at `pageSize` up to 100 and follows `nextToken` until `--limit` (at most 1000) containers are found. `archiveReason` is not sent, so Benchling's default (`NOT_ARCHIVED`) applies. List containers has no registry ID filter, so registry IDs are first resolved with [Bulk get registered entities](https://docs.benchling.com/docs/api/v2/benchling-api/registry/bulk-get-registered-entities), whose `entityRegistryIds` is a "Comma separated list of entity Registry IDs" with no documented maximum; the toolkit sends 100 per request and reports IDs absent from `entities` as `unregistered_ids`. That route needs a registry ID, so without `--registry` the toolkit reads [List registries](https://docs.benchling.com/docs/api/v2/benchling-api/registry/list-registries) and uses the only registry, or fails listing them.
- No V2 route returns a container's full location path. `container get --location` follows `parentStorageId` one [Get location](https://docs.benchling.com/docs/api/v2/benchling-api/locations/get-location), [Get box](https://docs.benchling.com/docs/api/v2/benchling-api/boxes/get-box) or [Get plate](https://docs.benchling.com/docs/api/v2/benchling-api/plates/get-plate) read per level, at most 10 levels. A container `parentStorageId` "can also specify a coordinate for plates and boxes (e.g. plt_2bAks9dx:a2)" (V2 contract); the coordinate is reported as a `well` or `position` item and not read separately.
- Each apply journal event stores the raw HTTP status of that write. A failure that never produced an HTTP response has no status.
