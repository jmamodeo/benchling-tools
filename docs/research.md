# Benchling API research record

Research date: 2026-09-24

Live contract checks on 2026-09-29 against a development entry in a test tenant:

- V3 document part objects are flattened `DocumentPart*` unions, consistent with the [entry guide updated on September 28](https://docs.benchling.com/docs/working-with-entries). The adapter recognizes sections and retains original raw part objects.
- V2 entry, folder, and project responses wrap their resources. Task responses can be flat status objects without an ID property; validate status rather than requiring a resource ID. Successful task responses return both UUID result IDs and canonical V3 `result_*` IDs; status polling persists those in the execution journal without inferring a per-record mapping from list positions.
- The public V2 OpenAPI still declares optional `AssayResultCreate.id`, but the tested tenant rejects that property in `/assay-results:bulk-create` with HTTP 400. The CLI therefore rejects caller IDs in table upload plans, omits remote IDs, and journals separate local correlation UUIDs. These are explicitly not idempotency keys. No write is automatically retried.
- The [result upload guide](https://docs.benchling.com/docs/example-creating-results) limits notebook table bulk requests to 500 records and distinguishes submission from browser integration. The initial upload state is `submission_pending`; only task success confirms `pending_integration`.
- Pending results are documented for both API versions. The V3 result guide ([Integrating the Results into the Table](https://docs.benchling.com/docs/example-creating-results#integrating-the-results-into-the-table)): "When results are created in this way, they are not immediately appended to the destination table. Their source is marked as "pending" and they will not appear in the table until they are explicitly integrated. To integrate pending results into a table, click the plug icon in the toolbar of the table." [Creating a new Notebook Entry containing Results](https://docs.benchling.com/docs/creating-a-new-notebook-entry-containing-results) repeats it for `batch_create` and bulk create, and says "V3 cannot create an entry from an entry template or fill a table at creation". The Benchling help article [How can I associate results with entries in bulk via the API?](https://help.benchling.com/hc/en-us/articles/13810222262285-How-can-I-associate-results-with-entries-in-bulk-via-the-API) (environment "API/SDK - all systems/versions") says `assay-results:bulk-create` "will still require you to manually confirm the upload in the notebook entry". The one documented direct fill is V2 entry creation from a template with `InitialTable` CSV data, which this toolkit does not do.

Authentication: Benchling's [authentication contract](https://docs.benchling.com/docs/authentication) specifies form-encoded `grant_type=client_credentials` at `/oauth/token`. App access tokens last 15 minutes; this grant does not issue a refresh token. Renew by repeating the token request. The same bearer token works for V2 and V3, with the app's own permissions and audit identity. `benchling-tools auth login` verifies that grant before saving the tenant URL and client ID in `environments.json` and the client secret in the OS keychain. A tenant URL may be a bare host or end in `/api/v2` or `/api/v3`; only `https` is accepted. Access tokens stay in process memory and are not written to the keychain or to `environments.json`. On a headless Linux host the keychain is an unlocked Secret Service reached by `DBUS_SESSION_BUS_ADDRESS`; there is no plaintext file.

The checksums recorded in `contracts/openapi-manifest.json` identify the exact public specifications reviewed. The YAML snapshots next to that manifest are those files. Tests validate the client's request bodies against them and do not need network access. List query parameters are also checked against `contracts/list-parameters.json`.

`scripts/check_openapi_drift.py` downloads the public V3 file from the URL in that manifest every Monday and on demand. A different SHA-256 fails the job and lists each `routes_used` path whose operation or referenced definition changed. The check uses the public spec only.

A parameter check on 2026-11-19 against those snapshots confirmed:

- V3 `GET /entry/items` documents `project.eq`, `schema.eq`, `name.anyOf`, and `modifiedAt.gt` / `gte` / `lt` / `lte`. It does not document `folderId`. Live tenants ignore `folderId` on that route.
- V2 `GET /entries` documents `projectId`, `schemaId`, `name`, `names.anyOf`, and one `modifiedAt` comparison string using `>` and `<`. The `listEntries` operation text does not repeat `folderId`, but the V2 components still define `folderIdFilter` (`folderId`, "Restricts results to those in the folder") and the historical SDK sends it. This client sends `folderId` only on V2, and uses `>=` / `<=` so a modified range stays inclusive. `name` is a single entry name (type string). `name.anyOf` and `names.anyOf` are comma-separated lists and document no escape, so a name that contains a comma is sent as V2 `name`. The V2 text describes `name` as the specified name and does not say the match is case-insensitive. `names.anyOf` does say case-insensitive, and that is what a name without a comma uses on V2.
- `GET /document-part-results-table/{document_part_results_table_id}` returns `rows` as a URL, plus `rowCount`, `columnDefinitions`, and `resultSchema`. `GET /document-part-results-table/{document_part_results_table_id}/rows/items` lists `StructuredTableRow` items. Its query parameters are `pageSize` (described as default 50, maximum 100) and `nextToken`. This client reads the part first and requires the rows URL to be that `/rows/items` path on the same tenant. `benchling-tools export` does not call a separate export endpoint. It pages these row reads, unstructured-table row reads, and `GET /result/items`, and writes the rows to a local JSON or CSV file. Those routes take a `v3_document_part` id (`docpart_…`). `results tables` lists V2 `results_table` notes whose `apiId` is a `v2_structured_table` id (`strtbl_…`). `GET /document-part-results-table/strtbl_…` is HTTP 404. `export --kind results-table --part strtbl_… --entry ENTRY` reads that entry's parts and uses the `DocumentPartResultsTable` whose handle, result schema, or sole results part matches the note. When none matches, it reads `GET /result/items` for the entry and the note's `assayResultSchemaId`. `--kind table` does not send a `strtbl_…` id to the unstructured-table route.
- V3 `Result` (`GET /result/items` and `GET /result/{result_id}`) is `IResult` plus `creator`, `entry`, and `schemaFields`. `schemaFields` is an array of `SchemaFieldValue`: `fieldDefinition` (a ref whose recorded properties are `id` and `__typename`), `value` (`BenchlingValue` or null), and optional `linkedEntityId`. It is not the V2 `fields` map. The recorded contract returns `schemaFields` on the result; `returning` is an optional field filter, and this client does not send it. Display names are `name` on the result schema's field definitions (`GET /result-schema/{id}/field-definitions/items`). `ObjectLinkValue.value` and `ObjectLinkListValue.value` are link objects (`id` plus `__typename`). Assay-result export writes one column per schema field under the display name, flattens each value to a scalar or a list of scalars, and keeps the result's scalar metadata (`id`, `createdAt`, `modifiedAt`, `archived`, `archiveReason`, `__typename`, and V2 `entryId` / `schemaId` / `projectId` when those keys are present). A null `value` exports as null (CSV `""`). `linkedEntityId` is written only when the field definition is a link type and the id is not the result's own id; an unset field's `linkedEntityId` is often that result id. Results-table and unstructured-table cells use the same flattening, so `ObjectLinkValue` and `ObjectLinkListValue` become ids in both JSON and CSV.
- V3 schema lists are `GET /entry-schema/items`, `/result-schema/items`, and `/run-schema/items`, each paged with `pageSize` (default 50, maximum 100) and `nextToken`.
- Dropdowns are `GET /dropdown/{dropdown_id}` and `GET /dropdown/{dropdown_id}/options/items` (unpaginated). A dropdown field points at the dropdown through `dropdownId` or `linkDefinition.id`.

The same day's check of the V3 spec `d2594d47…` and a live tenant set the write contract:

- `GET /document-part-unstructured-table/{id}` returns `rows` as a URL plus `rowCount`. Row pages are `GET .../rows/items` with `pageSize` at most 100. The only version is `versionMetadata.versionId`, and it is the entry version. Cell values use `inputValue.value` with `__typename` `TextValue`.
- `PATCH /document-part-unstructured-table/{id}` is gone (HTTP 405). Cell edits are `partsMutation.operationType` `update_table_cells`; appended rows are `insert_table_rows`. Both are `PATCH /entry/{id}` and both apply to unstructured tables. A stale entry version is HTTP 409 `Version mismatch`.
- Document insert uses `position`. Delete uses `sourceRange` `{start, end}`. Move uses `sourceRange` and `destinationPosition`. `coordinates`, `sourceCoordinates`, and `destinationCoordinates` are rejected as additional properties.
- `UpdateEntryInput.schemaFields` keys are field-definition IDs (`tsf_…`). A system name is HTTP 400 `schemaFields: Invalid field`. V2 result-record fields still use system names on `/assay-results:bulk-create`.
- `PATCH /result/{result_id}` updates one existing result. The body is `UpdateResultInput`. `schemaFields` is an object of `FieldValueInput` (`{"value": ...}`). The schema does not name those object keys. This client sends field-definition ids, the same key shape `UpdateEntryInput.schemaFields` uses, and does not send display names. The operation publishes no version field. A plan records `modifiedAt` from `GET /result/{id}` and re-reads every result before the first PATCH. A mismatch is a conflict and nothing is written. HTTP 409 is a conflict. CSV input maps export's display-name columns onto those ids at plan time.
- V3 `GET /entry/items` ignores a `folderId` query parameter. It is not in that operation's parameter list. V2 `GET /entries` still accepts `folderId`.

Contract decisions that still hold:

- `UpdateEntryInput.schemaFields` values are `FieldValueInput` objects, each containing exactly `value`.
- V2 `AssayResultCreate.fields` explicitly requires system-name keys, and `/assay-results:bulk-create` returns a task ID for polling at `/tasks/{task_id}`.
- V2 entry `results_table` notes expose both the structured-table `apiId` and `assayResultSchemaId`, which are used rather than matching a visible table name or position.
- `DocumentPartResultsTable` exposes `columnDefinitions` and a rows URL. `DocumentPartUnavailable` returns only the fields shared by every document part.
